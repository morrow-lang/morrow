# Real browser and WASM codec experiment

This harness executes the existing JSON, CBOR and protobuf adapters in a real
Chromium browser. It does not replace the production wire protocol. Each generated
module links one selected codec; native callers retain the existing runtime
`Codec` selection API. All authored orchestration is Rust. The embedded JavaScript
is a measurement driver, and the JavaScript module adapters are generated by
wasm-bindgen.

## Observed September 14, 2026 run

Apple M4, 24 GiB RAM, macOS 26.5.1 (25F80), Microsoft Edge 153.0.4234.32,
Rust 1.100.0-nightly (f248f4038, 2026-09-05), wasm-bindgen 0.2.128. Project
builds and other project benchmarks were paused during measurement. An unrelated
Raycast process was observed using approximately one CPU core and OrbStack about
9% of a core during a process sample; this was an ordinary desktop, not an isolated
benchmark machine. Codec and phase rotation reduce order bias but do not remove
background interference. The [raw observations](browser-results-20260914.json)
retain all 138 rows, nine batch means per phase, iteration counts, artifact sizes,
source fingerprints and versions.

This run demonstrates a real encoding/decoding and byte-transfer cost for JSON.
Among these particular validated adapters, protobuf was the strongest decoder and
had the smallest experimental module, while CBOR encoded large snapshots slightly
faster and used slightly fewer wire bytes for some payloads. Choosing a standard
also requires closed-schema validation, version negotiation, integer semantics,
tooling, migration and whole-message-path measurements. These results justify
evaluating a binary default; they do not by themselves establish application
throughput or a production-ready protobuf profile.

The subsequent production promotion preserves all 46 fixture byte encodings,
checked by `production_protobuf_keeps_the_measured_fixture_wire_bytes`. Production
adds preallocation identity/label/task limits and an explicit error-name registry;
the measured prototype adapter remains unchanged. Recorded source and lockfile
fingerprints describe the measurement snapshot before that production promotion,
not a promise that later builds have identical artifact hashes or timing.

## Reproduce

Use the repository's pinned Rust toolchain, its matching wasm-bindgen 0.2.128,
the `wasm32-unknown-unknown` target and a local Chromium/Chrome/Edge executable.
Set `CARGO_TARGET_DIR` to an absolute scratch path, `CARGO_BUILD_JOBS=2` and
`WASM_BINDGEN` to the wasm-bindgen executable. The two output paths must be new.

```sh
cargo test --manifest-path benchmarks/network-codecs/Cargo.toml --locked
cargo clippy --manifest-path benchmarks/network-codecs/Cargo.toml --locked --all-targets -- -D warnings
cargo run --manifest-path benchmarks/network-codecs/Cargo.toml --locked --bin browser -- prepare /tmp/fern-codec-browser-assets-new
cargo run --manifest-path benchmarks/network-codecs/Cargo.toml --locked --bin browser -- run /tmp/fern-codec-browser-assets-new '/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge' /tmp/fern-codec-browser-results-new.json
```

Preparation creates three release WASM modules and their generated glue, records
SHA-256 fingerprints and raw/gzip (`gzip -n`) sizes, and includes compiler and
wasm-bindgen versions. It uses thin LTO, one codegen unit, stripping and no wasm-opt.
The runner owns a fresh private browser profile and process group, serves a fixed
allowlist of assets on loopback, caps the result at 2 MiB, and terminates after five
minutes. It does not change the user's running browser profile or disable its
sandbox. The local origin uses isolation headers to permit a precise performance
clock; that is measurement infrastructure, not a production deployment requirement.

## Correctness and timing contract

Before timing, each WASM module checks independent fixed Join wire bytes, signed
64-bit extrema and values outside JavaScript's exact-number range, Unicode,
truncation, oversized inputs, missing/duplicate/unknown fields, all 46 fixture
round-trips and wrong message directions. The JavaScript/WASM boundary additionally
checks exact typed equivalence of each transferred byte array and exact JSON text
output. These are prototype acceptance tests, not proof that all three formats
accept exactly the same set of malformed encodings. In particular, binary
canonicalization and schema-evolution policy remain separate design questions.

Every fixture runs all codecs in a deterministically rotated order; phases rotate
by fixture too. Each phase warms up, calibrates a bounded iteration count to at
least approximately 8 ms per batch when possible, then records nine raw batch means.
Each observation is a nanosecond-per-operation batch mean, not a per-message tail
latency. Timed Rust decode includes validation, conversion to actual Fern protocol
types and destruction. Timed encode includes actual-message-to-wire adaptation,
encoding and destruction. Rust `black_box` and JavaScript checksums retain work.

The reported phases distinguish:

- **Within WASM:** one exported call runs the whole batch. This isolates codec work
  from repeated JS/WASM calls and byte transfers.
- **Byte-array boundary:** every operation crosses the wasm-bindgen boundary.
  Decode copies a JavaScript `Uint8Array` into WASM; encode returns a copied
  `Uint8Array` to JavaScript. Binary codecs could use this with binary WebSockets.
- **JSON string boundary:** every operation transfers JSON as a JavaScript string,
  including UTF-8 conversion. This reflects the current text-WebSocket host's
  representation more closely than the byte-array experiment.
- **Copy-only controls:** the same input/output representation crosses the boundary
  without parsing or encoding. These are independent timings, not quantities that
  can safely be subtracted from unrelated batch medians.

Input data is reused and warmed. The experiment includes neither WebSocket framing,
TLS, network scheduling, server mutation/checkpoint work, reactive UI updates nor
DOM rendering. It does not measure application throughput or cold navigation.
JavaScript output allocation and its GC can affect boundary timings. The runner
does not force GC or claim allocation counts.

Artifact sizes include the fixture corpus, acceptance checks and benchmark exports.
The JSON module additionally exposes text-boundary controls. They are complete
experiment artifacts, **not** the incremental size of adding one codec to the
production application, which may already use JSON for offline storage or HTTP.

WASM memory measurements are linear-memory capacity before fixture preparation,
after preparation and after the run. Capacity is page-granular, contains the
retained corpus and runtime/allocator space, and ordinarily does not shrink. It is
neither live memory, peak allocation accounting, total browser RSS nor a leak test.
