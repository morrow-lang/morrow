# Stage3 context specialization: concrete preimplementation map

Read-only inspection, 2026-09-19, OTP worktree after stage2 compiler release. This is an implementation proposal, not implemented or tested acceptance. No repository files changed and no builds run.

## Frozen descriptor16 decision

`Supervisor.ChildKey(M)` uses kind16, count1, children[0]=canonical mailbox descriptor M, arities=null. The child is a type constraint, exactly as Pid kind6; it is not one payload field. Kind15 Handle and kind17 ChildSpec keep count0. This supersedes the earlier undecided side-mailbox-metadata paragraph in the original compiler contract.

Actual existing paths inspected:

- `lowering/actors/descriptors.rs::actor_shape` emits Pid as `(6, [[M]])`; add ChildKey as `(16, [[M]])`. Descriptor identity remains deduplicated by complete semantic type, so ChildKey(Int) and ChildKey(String) differ.
- `managed/cost.rs::descriptor` traverses descriptor children, independently of payload traversal. Extend accepted kind range and its one-child group `2|5|6` with16. Validate child graph, bounds and work exhaustion exactly once through existing traversal/cache machinery. This validation traversal is intentional; it does not read a key payload using M.
- `cost::Cost::value` has a dedicated kind6 arm: validate invocation/Pid, compare stored mailbox pointer with children[0], charge wrapper size, never recurse into the mailbox as a value. Kind16 needs the same shape: validate key epoch/token/mailbox, charge wrapper/control ownership as the frozen accounting contract requires, never call value(M, key bits).
- `managed/copy.rs::Copy::value` kind6 copies a Pid wrapper and retains its external control. Kind16 likewise copies/retains the key wrapper and immutable token; do not put16 into unboxed kind5 or tuple kind3 arms. Preserve shared-key copy memoization by `(source address, descriptor address)` and both Heap/Fragment destinations.
- GC is conservative over actual allocation words, not descriptor children. Key wrappers must be initialized full words and retain their external control; no GC roots are inferred from count1. ChildSpec remains a separate internally pointer-bearing package and must traverse/copy its actual template graph despite count0.
- Current stage2 code rejects16; the above are required new arms, not an assertion that kind16 already works. Reject count0/count2/null/malformed child descriptors, mismatched native key mailbox, and same-name different token. Use a mailbox requiring pointer dereference (String or tuple) with a key wrapper whose first word is an external control pointer to prove cost/copy do not interpret mailbox payload at key offset.

Compiler `Type::ChildKey(Box<Type>)` is the smallest generic opaque representation. Add it beside Pid in parse/type/display, module qualification, inference unification/resolution, nominal substitution/generics, alias expansion, scheme capabilities, recursive type walks, native layout validation and actor sendability. It remains opaque: no public constructor, destructuring or arbitrary fields. M participates in type identity/validation but not Result containment as owned message payload (follow Pid's existing treatment). New NativeType leaves suffice for Handle/ChildSpec; child template validation is a runtime graph boundary. Audit exhaustive Type matches rather than cloning a second type walker.

## Concrete effect representation and pass order

Existing places that matter:

1. `check.rs::Signature` has only mailbox; `actors::attach` infers actor-only effects over `dependencies::owned_calls`, excluding nested lambdas. `Checker::function` resets mailbox from Signature. Treating Supervisor.start/current/stop as actor-only would reject valid root helpers. Leaving them ordinary would call a root driving adapter from an actor.
2. `check/specialize.rs::Driver` already checks source templates on demand. Key is `(template, Vec<Type>)`, and target_types already includes mailbox in generic substitution. Extend this existing worklist, not a post-lowering clone pass.
3. `check/lift.rs` runs only after source specialization. That is the right ordering: each context-specific lambda body is checked and its target IDs rewritten before lifting.
4. `lowering/actors/lower.rs` already creates entry and returning CPS copies for every function.mailbox. Specialized actor functions can reuse this machinery; root copies remain ordinary functions with explicit managed Exec propagation.

Add `Signature.contextual: bool` independently of existing mailbox, and a specialization context key `Plain | Root | Actor(Type)`. Plain canonicalizes context-insensitive helpers so existing ordinary helpers are not duplicated. Actor-only signatures retain their existing mailbox inference and reject root invocation. Contextual means code selection depends on caller context; it does NOT by itself mean constructing a closure suspends.

Compute contextual sensitivity with the bounded dependency graph, including references and lambda bodies: a helper that creates a closure targeting a contextual helper must itself receive context-specific closure code. Reuse `dependencies::analyze_with_work`/its graph instead of attributing nested-lambda effects to the owner in `actors::attach`. Propagate the contextual bit transitively through SCC/reverse edges. Keep owned actor requirements on the existing separate graph. This conservative context sensitivity avoids needing a new unbounded local-closure dataflow analysis: a local closure that is constructed and subsequently invoked cannot hide its context-dependent body. Merely constructing an actor closure still does not make main actor-only.

In `Driver::{Instance,seen,enqueue,target_types,rewrite}`, carry context explicitly. Recheck a contextual helper in Root with mailbox=None or Actor(M) with mailbox=Some(M). Do not rely on source signature.mailbox for the override: `Checker::function` currently overwrites it. Include the context in recursive deduplication before checking body; enforce existing MAX_FUNCTIONS and graph/node budgets over both variants. A contextual helper called by two actor mailbox types receives distinct actor instances even when all ordinary arguments and result types are identical. Its ordinary source generics still use existing capture_pairs/substitution.

Direct calls choose the caller's context. In an actor instance, check contextual calls through ActorExpr::Call with the caller mailbox so strict operand normalization and returning-helper CPS work unchanged. Root calls remain ordinary direct calls to a Root instance. Actor-only entry creation (Process.spawn, Supervisor.worker) selects Actor(M), even when construction occurs at root. Root export/main demands Root; unused contextual templates may be proof-checked at root, but cannot force creation of an actor instance with invented Unit mailbox. Existing mailbox generics remain inferred by actual entry demand.

## Callable boundary: required small extension, not a root-driver escape

Current `closures::invoke` accepts only Type::Function. ActorFunction is accepted as an entry, not an arbitrary local call. `actors/contracts::validate` rejects every first-class managed helper with mailbox=None except direct spawn. `lowering/actors/dynamic.rs` dispatches only ordinary callable targets with mailbox=None, and falls back to an ordinary native call. These are real implementation sites; the context key alone is insufficient.

Recommended sealed internal `Type::RootFunction(Box<Type>)` marker for root-bound contextual callable values, alongside existing ActorFunction(M, Function(...)). RootFunction is not a source-namable new function annotation. At a contextual named function value/lambda, use expected actor entry mailbox when provided; otherwise instantiate in the current context. A context-sensitive lambda created in Actor(M) is ActorFunction(M,...); one created at root is RootFunction(...). Ordinary context-insensitive lambdas remain Function.

Extend `closures::{lambda_body,invoke}`, callable decomposition, specialization FunctionValue rewriting and lift::lambda to preserve this identity. RootFunction invokes only at root; ActorFunction invokes only with compatible owner mailbox and generates actor suspension-capable IR. Neither implicitly unifies with ordinary Function callback parameters. An explicitly root-bound callable cannot be captured into an actor and run a root adapter. A named contextual function may still be instantiated afresh as an actor entry; this is distinct from converting an existing root-bound closure with captures. Source callback/container escape tests must check these distinctions.

For actor indirect invocation, reuse `dynamic.rs` bounded identity dispatch and capture extraction, matching Actor(M) candidates with exact params/result/mailbox. Do NOT retain the synchronous native fallback for actor-effectful callables: an unmatched identity is checked fault11. Ordinary Function dynamic calls retain their existing fallback. Public IR validation must reject an ActorFunction closure target whose function.mailbox disagrees, root markers in actor invoke/captures, and forged ordinary Function closures targeting root-driving helpers. Generated private control nodes remain sealed. This introduces context-sensitive callable support only; list.map/JSON/FFI ordinary callbacks do not gain suspension.

Parent accepted this sealed RootFunction marker after review, including no implicit ordinary-callback or actor-capture conversion and continued fresh actor-entry instantiation. A more general effect-polymorphic Function representation would touch more existing APIs without helping this bounded stage. Simply erasing root markers is unsafe.

## Supervisor lowering and obligations

Add dedicated `supervisors.rs` operation enum/walkers, `check/supervisors.rs` and `check/nominal/supervisors.rs`, and `lowering/actors/supervisors.rs`; reuse existing namespaced builtin dispatch and canonical nominal registration. Constructors/id are synchronous managed calls. start/current/stop carry resolved Root/Actor request mode; start_link and startup operations require actor context.

Actor request lowering belongs in Builder::expression/needs plus normalization, next to receive: evaluate operands once left-to-right; make an immutable resume closure capturing lexical locals/return continuation; emit sealed SuspendSupervisor; finish the physical callback with returned scheduler status. Do not emit ScopeLeave on suspension and do not use the self-tail reusable frame path. Resume first receives the operation result, then invokes the existing continuation/result matching. Root operations emit the separate root adapter, never actor polling loops.

Extend Plan with immutable request registrations, binding opcode, exact canonical request type, exact result type, resume function identity. Emit these in descriptor publication alongside Function descriptors without changing Function. A separate registration ABI is still needed; the old function table cannot encode these four relationships. Registration identities should be compiler-owned immutable addresses validated once by runtime before admission.

Parent accepted `take_reply(exec, registration, out_root_slot)->status`. Add a roots.rs helper returning an address of a reserved initialized native root word. The function-entry root frame must already register it before the call. Runtime stores reply in this root slot before clearing Actor reply storage; compiler loads result after fault/status checks. Returning an unrooted word and clearing Actor first does not meet the explicit ownership contract. Root driving results use normal assign/root_value before any collecting operation. Registration and root-membership details are now proposed in `supervisor-registration-abi.md`.

Result duties remain in existing obligations engine. start/current/stop and init_ack produce ordinary canonical Result types, so no bypass. init_ignore/init_fail use Type::Never and the stage2 terminated/exits summary distinction: earlier Result obligations survive; a handled Result in an unreachable successor does not count; cleanup captured duties retain existing loop credit. Add startup terminal nodes to gate/expression/substitute/walkers and strict divergence handling. Deferred callbacks, receive guards, REPL and ordinary collection callbacks keep current actor-effect restrictions.
